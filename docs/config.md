# Kiosk configuration

The kiosk reads one JSON file, `/etc/sfo-kiosk/config.json` by default
(`--config`, or `GHAF_SFO_KIOSK_CONFIG`). In an SFO image it is generated by
`modules/services/kiosk/default.nix` in `ghaf-sfo-laptop`; nothing here is meant to be edited by
hand on a device, but it is plain text on purpose so that `cat`-ing it on a serial console tells you
what the kiosk is actually running.

## Top level

| Key          | Type   | Default | Meaning                                       |
| ------------ | ------ | ------- | --------------------------------------------- |
| `version`    | int    | —       | Schema version. **Required.** See below.      |
| `title`      | string | `"SFO"` | Shown at the left of the status bar.          |
| `buttons`    | array  | —       | **Required, non-empty.**                      |
| `status_bar` | object | —       | Clock, battery, network.                      |
| `layout`     | object | —       | `columns` (int, default 3).                   |
| `exit`       | object | —       | `label` and `icon` for the small exit button. |

### `version` is not ceremony

This file is the only contract between two repositories that bump independently. A binary refuses a
`version` higher than it understands, and says so, because the alternative — quietly ignoring a
field a newer nix module added — surfaces as "the button does nothing", which is the least
diagnosable failure the system can produce.

Within a version, **unknown fields are ignored rather than rejected**, so a newer nix module adding a
field to an existing action kind does not brick an older binary.

## Buttons

```jsonc
{
  "id": "plan",                       // [a-z0-9-]+, stable, appears in the journal
  "label": "Plan",                    // what the operator reads
  "description": "Mission planning",  // tooltip, optional
  "icon": "map-symbolic",             // theme name, or an absolute path
  "action": { ... }
}
```

Order comes from the nix module, which sorts before writing; the array order here is the display
order.

## Actions

### `exec` — run a command in the gui-VM

```json
{ "kind": "exec", "argv": ["cosmic-settings", "network"] }
```

`argv` is an array, never a shell string. The kiosk executes it directly, so there is no shell, no
quoting rules to get wrong, and nothing to inject into.

### `givc-app` — start an application in another VM

```json
{
  "kind": "givc-app",
  "vm": "flatpak-vm",
  "app": "run-flatpak-app",
  "args": ["http://org.example.App"],
  "givc_cli": ["/nix/store/…/bin/givc-cli", "--name", "admin-vm", "…"]
}
```

`givc_cli` is the fully resolved command and connection arguments, produced by the nix module from
`config.ghaf.givc.cliArgs`. It is an absolute store path because `givc-cli` is only on `$PATH` in
gui-VM on debug images.

**`app` is the GIVC application id, which ghaf derives from an application's `desktopName` and not
from its `name`** — lowercased, spaces to dashes. The two are routinely different. ghaf's own
flatpak VM declares an application called `flatpak-run` whose id is `run-flatpak-app`, because its
`desktopName` is `"run Flatpak App"`. Getting this wrong produces a button that does nothing, with
the only evidence an "application unknown" line in the _target VM's_ journal. `ghaf-sfo-laptop` has
a build-time check (`checks.kiosk-buttons-name-real-apps`) for exactly this.

On `args`: GIVC validates every argument in the target agent against declared types, and only `url`
(http/https) and `flag` are usable downstream — the `file` type needs a `directories` whitelist that
ghaf's app-VM wiring never sets. This is why ghaf smuggles flatpak app ids through as
`http://<app-id>`; the receiving script strips the scheme. Prefer passing nothing at all and baking
policy into the target VM.

## What happens when something is wrong

One bad button never takes the kiosk down.

| Condition                                             | Result                                                            |
| ----------------------------------------------------- | ----------------------------------------------------------------- |
| Unknown `kind`, or a missing field                    | Button renders **dimmed**; pressing it says why                   |
| Command cannot be spawned                             | Red banner with the error; full argv at `error!` in the journal   |
| Command still running after 20 s                      | Killed, and the banner says so                                    |
| Malformed JSON, `version` too new, or `buttons` empty | **Fatal.** The kiosk exits non-zero and the desktop shows through |

That last row is the deliberate exception: a kiosk that starts with no buttons hides the desktop and
offers nothing, which is strictly worse than failing loudly into the journal.
